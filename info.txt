What is Technical Debt? (The College Project Analogy)
Imagine you are building a full-stack web application—like a centralized management system with a React frontend, a Node.js backend, and a PostgreSQL database. The deadline is tomorrow. To get it working, you copy-paste the same database connection code into five different files. You also cram the logic for registering a user, updating their profile, and sending them an alert all into one giant, 500-line Express route.
It works, and you get the grade. But that messy, copy-pasted code is Technical Debt. If you want to add a new feature later, that messy code makes it a nightmare to update.
The AI Technical Debt Inspector is a system that automatically finds this messy code in your repository, explains what it is doing, and writes the cleaner, optimized version for you.
How It Works: The "Team" of AI Agents
Instead of thinking of this as one giant, magical AI, think of it as a few small Python scripts (Agents), each powered by an LLM, that have specific jobs. They talk to each other to get the work done.

The Repository Scanner (The Fetcher): This is a script that connects to your GitHub repository. It downloads your code and breaks it down so the AI can read it. It maps out how your files are connected (e.g., "File A imports File B").
2. The Static Analysis Agent (The Code Reviewer): This agent reads your code looking for bad practices. It flags things like Duplicated Logic (finding the same chunk of code in three different files) or Poor Architecture (finding a "God class"—a single file that tries to do everything instead of being split up into smaller, modular files).
3. The Security Agent (The Guard): This agent reads the code specifically looking for vulnerabilities. For example, it will flag if you accidentally hardcoded a database password or if your SQL queries are written in a way that allows a hacker to inject malicious code.
4. The Refactoring Planner (The Fixer): This is the smartest part of the system. It takes the problems found by the Reviewer and the Guard. Because it understands Python, JavaScript, SQL, and other languages, it actually writes the corrected code. It then generates a "Pull Request" on GitHub, offering the clean code for you to approve.
The Main Feature :  Code Comprehension
If a normal tool finds a 500-line messy function, it just throws an error: "Warning: Function is too long."
The AI Inspector is different because it reads and understands the intent. Before it tries to fix the code, it generates a plain-English summary.

It will say: "This chunk of code in routes.js is currently registering a user, creating a token, and updating the Postgres database all at once."
Then it will say: "Here is a plan to split this into three separate files to make it easier to read and maintain."
How You Would Actually Build It (The Tech Stack)
If an engineering student were to build a basic version of this for a final year project, here is the tech stack they would use:

Backend/Frontend: A Node.js and Express server with a React frontend to create a dashboard where users can see their code issues.
AI Logic: Python scripts using a library like LangChain to create the "Agents" and send the code to an LLM (like Gemini or OpenAI).
Database: PostgreSQL / neo to store the history of the scans and the list of bugs found.
In short, it is like having a senior developer living in your GitHub repository, constantly reading your commits, summarizing what they do, and politely offering to clean up your messy code before it becomes a major problem.

The system creates automated Jira tickets for large architectural overhauls.

This follows the orchestrator-worker pattern: the AI orchestrator itself never touches the code directly — it dispatches work to the Repository Scanner, then to the Static Analysis and Security Agents in parallel, and every worker reports its findings back up to the orchestrator (that's the dashed loop on the right) rather than passing results peer-to-peer. What triggers the pipeline when a developer commits code?

The trigger is a GitHub webhook. Here's the mechanics of it:

Webhook registration — When you set up the AI Inspector on a repo, it registers a webhook with GitHub (via GitHub's API) for specific events — typically push and pull_request events.
Event fires — The moment you git push (or open/update a PR), GitHub's servers immediately send an HTTP POST request to a URL your system exposes — this is the "listening" endpoint on your Node.js/Express backend.
Payload contents — That POST request carries a JSON payload with metadata: which repo, which branch, the commit SHA(s), the list of changed files, and who made the commit. Critically, it does not send the full code — just pointers to what changed.
Backend reacts — Your Express server receives this payload, verifies it's authentic (GitHub signs webhooks with a secret so you can confirm it's not spoofed), and then kicks off the pipeline — typically by handing control to the Python orchestrator, often via a message queue or a direct API call.
Scanner takes over — Only at this point does the Repository Scanner actually clone or pull the changed files and start parsing.
For a presentation, a good detail to include: this webhook-driven design is what makes the system feel "always-on" rather than something a developer has to manually trigger — it mirrors how CI/CD tools like GitHub Actions or Jenkins already hook into the commit lifecycle, so it fits naturally into existing developer workflows without adding friction.

How does the Python AI orchestrator coordinate the agents?

The orchestrator's job isn't to write code or run analysis itself — it's a coordination layer that manages state, sequencing, and handoffs between agents. Here's how that typically works with a framework like LangChain:

1. Maintains a shared "state" object
Rather than agents talking peer-to-peer, the orchestrator holds a central state object (often a JSON structure) that starts with just { commit_sha, changed_files } and accumulates fields as each agent contributes — ast, then issues[], then vulnerabilities[], then refactor_plan. Each agent reads what it needs from this state and writes its output back into it. This is sometimes called the blackboard pattern.

2. Sequences the calls (with some parallelism)
The orchestrator enforces dependency order: the Repository Scanner must finish before analysis can begin, since Static Analysis and Security both need the parsed AST. But once the AST is ready, it can invoke the Static Analysis Agent and Security Agent concurrently (async calls) since they're independent of each other — that's the parallel branch you saw in the diagram.

3. Uses structured outputs, not free text
Each agent is prompted to return a strict JSON schema (e.g., { "issue_type": "...", "file": "...", "line": 12, "severity": "high" }) rather than a paragraph. This lets the orchestrator programmatically merge, filter, and rank results from multiple agents without needing another LLM call just to parse prose.

4. Handles retries and tool calls
If an agent's LLM call fails, times out, or returns malformed JSON, the orchestrator retries or falls back to a simpler rule-based check. It's also the layer that exposes "tools" to agents — e.g., giving the Refactoring Planner a read_file(path) function so it can pull exact code context instead of hallucinating it.

5. Decides when the pipeline is "done"
Once the Refactoring Planner returns a plan, the orchestrator checks a simple rule: is this fix small and isolated? → auto-generate a PR. Is it a large architectural change? → route it to create a Jira ticket instead (as in your Phase 4). This routing logic lives in the orchestrator, not in any individual agent.

A good way to phrase this for your presentation: the orchestrator is less like a manager assigning tasks from scratch each time, and more like a relay race baton — a single evolving context object gets passed from agent to agent, each one adding their piece before handing it forward.
